Architecture

codec is one Go binary. It carries a web UI (built with Svelte and embedded at build time), an HTTP server that only listens locally, a CLI, and an engine that both of them use. This page explains the parts and how they fit — no code knowledge needed.

The big picture#

Adapters (server, CLI, workspace, config, schema cache) do the input and output; the engine only reasons about text it is given.

Engine and adapters#

The most important rule in codec's design: the engine decides what things are; adapters decide where they come from and how they look.

  • Engine packages take file contents and return structured answers: "this document is a Deployment", "this value was set by values-prod.yaml line 2", "this job runs after build". They never read files, touch the network or look at the clock, which makes them fast to test and identical in the UI and the CLI.
  • Adapters do everything else: the workspace reads files through a read-only guard, config reads and writes the settings file in your profile, the schema cache downloads and stores schemas, the check adapter combines lint and schemas, the web server and the CLI turn requests into engine calls.

Because both front ends call the same engine, codec yaml lint in CI reports exactly what the editor shows.

File types: the provider model#

Each kind of YAML is handled by a provider. A provider answers a few questions about a file — "is this mine, and how sure am I?", "what is its outline?" — and optionally more: hover, go to definition, completion, diagnostics.

Adding a file type means adding a provider. The concepts mirror the Language Server Protocol, so a future codec lsp can reuse them.

Lens views (Helm, Resources, Argo, Pipeline, Compose, Ansible) sit on top: each has its own engine package that understands the whole project — every file of a chart, every include of a pipeline — and an API endpoint the view calls.

The web UI#

The UI is a single-page app compiled into the binary; it needs no internet and loads no third-party resources. It talks to the server only through a small API layer, which keeps a future desktop app (Wails) a matter of swapping the transport.

  • Shell — sidebar (rail), tabs, command palette, status bar.
  • Shared components — buttons, tree, editor wrapper (CodeMirror), graph (dagre layout), dialogs, skeletons.
  • Features — one folder per view or tool: workspace, editor, helm, lint, compare, kube, argo, ci, compose, ansible, scaffold, and the encode/decode tools.
  • State — tab state lives in memory; display preferences in local storage; nothing pasted is stored.

Live updates arrive over Server-Sent Events: a folder was opened, files changed, file types are ready.

Repository layout#

cmd/codec/            entry point: starts the CLI
internal/
  yamlkit/            engine · YAML parse with positions, templates, diagnostics, diff, layered merge
  provider/           engine · file-type detection, outline, hover/definition/completion interface
  lint/  schema/      engine · lint rules and deprecations · schema choice and validation
  helm/               engine · Helm SDK render from memory, values provenance
  kube/               engine · objects, relationships, inventory, neat, Kustomize
  argo/  ci/          engine · workflow resolution · GitHub/GitLab/Azure pipelines
  compose/  ansible/  engine · Compose merge and variables · playbooks, roles, precedence
  query/  textdiff/   engine · jq over documents · text diffs and patches
  scaffold/           engine · starters, clone-with-rename, snippets
  names/  codec/      engine · "did you mean" · base64/JSON/JWT/Ansible-log tools
  workspace/          adapter · read-only folder access, file index, watcher
  config/  schemacache/  sample/   adapters · settings file · schema downloads · the sample repo
  check/              adapter · lint + schemas for editor, workspace, renders and CLI
  web/  cli/          adapters · HTTP API and embedded UI · commands
  version/            build identity
frontend/src/
  lib/                api client, shared components, shell, stores, styles (design tokens)
  features/           one folder per view or tool
docs/                 this site (plain HTML and CSS) and screenshots
design/               architecture, decisions, conventions, design language, workflows
scripts/              dev.sh (build and run), perf.sh (performance budgets)

More detail for contributors is in design/architecture.md in the repository.

Performance#

codec is built to feel instant on real repositories. The budgets below were measured on a Windows laptop with scripts/perf.sh, which generates the test inputs and times them; run it yourself to check your machine.

CaseBudgetMeasured
10,000-file repository: open and list≤ 1 s0.7–0.9 s
10,000 files: every file typed≤ 10 s1.4–2.2 s
Go to file, per keystroke≤ 100 ms13–62 ms
Lint 6,000 YAML files≤ 30 s6–7 s
5 MB file: shown in the editor≤ 2 s0.9 s
5 MB file: typing≤ 16 ms per key6.8 ms
Chart rendering 500 documents≤ 2 s0.12–0.19 s

How: documents of a file are parsed in parallel; long trees draw only the rows on screen; outlines of huge files keep fewer levels; file types are classified in the background after the tree appears; schema downloads start together and never block a render.
