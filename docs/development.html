Development

How to build codec, work on it, and change it in a way that fits the rest. The repository's design/ folder holds the detailed rules; this page is the overview.

Setup#

You need Go 1.26+ and Node.js 22+. On Windows, Git Bash runs the scripts.

git clone https://github.com/mahasenabheetha/codec.git
cd codec
npm --prefix frontend ci           # once: UI dependencies
scripts/dev.sh run                 # build the UI and the binary, serve on :8766
scripts/dev.sh ui                  # the same, plus a hot-reloading UI on :5173

Fixing a bug#

  1. Reproduce it with the smallest input — ideally a file in the sample repository or a few lines of YAML. Note the exact message or behaviour.
  2. Find the layer. If the CLI shows the same wrong answer, the bug is in the engine; if only the UI is wrong, it is in internal/web or the frontend.
  3. Write a failing test first in the engine package: a named table-driven case with the input that broke. Every fixed bug keeps its regression case.
  4. Fix it at the source, in the same style as the code around it: small functions, comments that explain why, no new dependencies without a reason.
  5. Run the tests for that package and check the UI if it is visible there.
  6. Record it: a line under "Fixed" in CHANGELOG.md; update this site if the behaviour it describes changed.

Adding a feature#

  1. Write it down first in design/roadmap.md: the problem, the user-visible result, and what "done" means.
  2. Check the decisions in design/decisions.md. If the feature needs a new choice, add a numbered decision.
  3. Engine first. Put the logic in an engine package, pure and tested. A new file type is a new provider; a new view is a lens package plus a provider.
  4. Then the adapters: an API endpoint in internal/web, a CLI command in internal/cli where it makes sense.
  5. Then the UI, from the shared components and the design language: a palette entry, empty and loading states, keyboard access.
  6. Document it: a page or section on this site, a screenshot of it on the sample repository, the README feature list, the CHANGELOG.

House rules#

  • codec never writes to the folders it opens. What-if only.
  • No settings or files in the user's repositories; settings live in the user profile.
  • Engine packages have no input or output of their own.
  • No runtime calls to third parties except schema downloads.
  • Nothing pasted into tools is persisted.
  • Work on a feature branch and open a pull request; main is released from tags.

Editing this site#

The site in docs/ is plain HTML with one stylesheet — no build step. Each page repeats the sidebar; when adding a page, add its link to the sidebar of every page and set the previous/next links around it. Screenshots are 1400×820 captures of the sample repository. GitHub Pages serves the folder as is.

Releasing#

Merge to main, update the CHANGELOG, then push a tag (v2.1.0). The release workflow builds binaries for six platforms, publishes a GitHub Release with checksums, and pushes the Docker image (latest only for stable versions). Details: design/releases.md.
