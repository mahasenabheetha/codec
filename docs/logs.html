Log viewer

Tools → Log viewer reads structured logs of any common format into one shape — time, level, message, source, error, stack, fields — so you can filter, chart and read them. It is built for the logs of Kubernetes workloads and pipelines (argo logs, kubectl logs) and for any service that logs JSON or key=value. No folder is needed, and nothing is stored.

Opening logs#

  • Open logs…, or drop files anywhere on the tool. Each log you open gets a tab of its own, so you can keep several runs open and switch between them; each tab keeps its own search, time range and selection. Several files opened together are read as one log, merged by time; Add to this tab… (or Shift while dropping) merges more into the current tab. Each file is a chip you can remove.
  • Paste with Ctrl+V anywhere on the tool, or use Paste… for a box.
  • In the Explorer, right-click a log file (.log, .ndjson, .jsonl, .txt, .out, .clef, gzipped, or rotated like .log.1) → Open in Log viewer; a file already open in a tab gets its tab back. The Explorer lists files up to 8 MB; open bigger ones as files.

Files may be gzip-compressed or UTF-16 (as PowerShell's > writes them). A log can hold up to 256 MB of text.

What it reads#

KindExamples
ECS JSONany ecs-logging library (Go ecszap, Java, .NET, Python, Node): @timestamp, log.level, message, error.*, trace.id; dotted or nested fields
Other JSONGo slog, zap, logrus, zerolog; Bunyan and pino; Serilog (message templates filled in); Docker's container log files; Kibana and Elasticsearch exports
logfmttime=… level=info msg="…" key=value: slog's text handler, logrus, Argo's own containers
TextKubernetes klog, Go's log package, lines that start with a date and time or a time of day alone (10:00:00.123 [main] INFO …, logback's default) and a level word; Go panics and Java, .NET, Node and Python stack traces, joined to the entry they belong to
Prefixesargo logs and stern pod names, kubectl logs --prefix and --timestamps, container runtime lines, docker compose logs, CI timestamps and colour codes are taken off and kept as the entry's source and time

Lines from different pods may interleave; a stack trace still joins its own pod's entry. A message that is itself JSON is read as fields too (msg.user.id). A line codec can't place is kept as a text entry, so nothing is lost.

The overview#

Above the entries: how many there are and over how long, the count per level (click one to show it and worse), the sources and formats, a link to the first error, the errors that repeat most (messages that differ only in numbers, IDs, UUIDs or quoted values count as one) and the longest silences, when nothing was logged.

Filtering#

Type in the search box and the entries filter as you go; the words you search for are marked in the rows. As you type, the box suggests field names, and once a field and : are there, the values it has — pick one with ↑ ↓ and Enter or Tab. ? shows what you can write, with examples from your log. Level: All · Info+ · Warn+ · Errors writes the level part for you. Terms are combined with AND.

QueryMatches entries…
timeout, "connection reset"containing the word or phrase anywhere, ignoring case
/time.?out/matching a regular expression (Go's RE2)
level>=warn, level:errorat or above a level, or at exactly that level
service.name:api, url.path:/api/*whose field has the value, ignoring case (* is a wildcard); field:* means the field is there
status>=500, latency<1.5scomparing numbers or durations
-logger:health, NOT …without the term
a OR b, (a OR b) c, level:(error OR fatal)either one; parentheses group

Short names reach the core fields whatever the log calls them: level, message, source, step, logger, caller, error, stack, trace, format, file. Any other name is a field (http.response.status_code, or log.level for the level as written). A field the log doesn't have is pointed out; with : it is searched as text instead, so http://… works.

Entries over time#

The chart counts the matching entries over time, stacked by level. Drag across it to keep only that time range; the range's chip clears it.

The entries#

One row per entry: time, level, source (when there are several), any field as a column (Columns; your choice is remembered) and the message. Lines: Wrap (the default) shows every cell whole, over several lines if need be; One line keeps each entry on a line and the list scrolls sideways. Time shows times in local time, UTC or since the first entry; a log without times has no time column and no chart, and the tool says so. Rows are fetched as you scroll, so 100,000 entries scroll like 100.

↑ ↓ (or J K) move through the entries, E and Shift E go to the next and previous error, / to the query, Esc closes the entry.

Around, folds and highlights#

  • Around: ±3 / ±10 shows that many entries before and after each match, dimmed, whatever the search hides — what led up to it. A row "⋯ 240 entries" stands for what is skipped between them.
  • Fold: Output folds each run of plain output (lines without a level, such as a database's own messages inside an Argo run) into one row, "⋯ 12 entries of output"; it is on when a log mixes structured entries with plain output. Click the row (or press O) to show the lines; fold on the first of them folds them again. Nothing is dropped.
  • Repeats folds the same line logged again and again by one source into one row with a ×120 badge and how long it went on; Similar also folds lines that differ only in numbers and IDs. Click the badge (or press O) to show them all.
  • Highlight takes up to four searches, each with a colour: matching entries get that colour on their edge, and nothing is hidden.
  • The strip beside the scrollbar shows where in the whole list the errors (red), warnings (yellow), highlights (their colour) and pins are, and the part you are looking at; click a mark to go to its entry (an error first), or anywhere else to go to that part.

The counts, the chart and the Errors tab always count the entries the search matched.

An entry#

Select a row for the entry in full: its message (JSON in it laid out), error, time, source, logger, caller and trace; its stack trace, with each frame's function apart from its file and the runtime's and frameworks' frames folded away; its fields as a tree; the entries just around it (±5, 20 or 50, whatever the query hides — what led up to it); and the line as it was read.

Next to any value: only this and hide this add a term to the query, the column button shows the field in the list, and for trace, span, request and correlation IDs follow replaces the query with that ID, so you see everything that happened to one request across the log.

Errors and fields#

Errors lists the warnings and errors of the matching entries grouped by message (numbers, IDs, UUIDs and quoted values don't split a group), most frequent first, with when they started and stopped and how many sources had them. Click one for its first entry; Show filters to it (group:3).

Fields lists every field of the matching entries: how often it is there, its most common values (click one to filter to it) and, for numbers, the minimum, median, 95th percentile, maximum and mean.

Argo runs#

An Argo workflow's log is read step by step. An entry's step is its argo_step_name field when it has one, what the other entries of its pod said, or else the pod's name, which Argo makes <workflow>-<template>-<number>; plain lines with no pod take the step of the entry before them. The list shows the step in place of the pod (the pod on hover), step:deploy filters to one, and Steps lists them in the order they started: when each ran, how long it took, its entries, errors and warnings, failed ones in red. Lines of Argo's own executor (its init and wait containers) count as output and fold with it.

Pins#

Pin the entries that matter while you investigate: P on the selected row, the pin at the start of a row, or Pin in the entry. Pins lists them in time order with a note each; [ and ] go from pin to pin, and the strip beside the scrollbar marks them. Copy as text or Copy as Markdown gives a short report — time, level, source, message and your notes — for a ticket or a chat, with likely secrets masked. Pins are kept in the tab's memory only; they are cleared when files are added to or removed from the tab.

Compare two runs#

Open the other run in a tab of its own (the one that passed yesterday, say), then Compare with… in this one and pick it. Messages are matched with their numbers, IDs, times and generated pod names masked, so a step logs the same message in both runs. Compare shows both runs in numbers, the first difference in each (the first entry whose message the other run never logs: where they part), and lists of what is new here, what is missing here (a step that didn't happen), what is logged more or less often, and each source with its entries, errors and how long it took, slower ones marked. In the new and missing lists, errors and warnings come first. A click opens the entry in either tab; Copy as text gives a short report with likely secrets masked. Files added to or removed from either tab make it stale until you compare again.

Export and copy#

The export button saves the matching entries as the lines they were read from (.log), as one JSON object each (.ndjson) or as a table with your columns (.csv). Alt C copies a short summary of the log; an entry's buttons copy its line or the entry as JSON. Whatever is copied has likely secrets masked — values of password, token, secret, key and cookie fields, bearer credentials, JWTs and passwords in URLs — so it is safer to paste into a ticket. Masking is a safety net; read what you share.

Where the log is kept#

The log is read by codec's server and held in its memory while you look at it — never written to disk. A log unused for an hour is let go, and so are the oldest when the logs held reach 1 GB of memory; the tool then sends it again from what it still holds, without asking. Closing the log, or codec, lets it go.
