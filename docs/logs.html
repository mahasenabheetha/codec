Log viewer

Tools → Log viewer reads structured logs of any common format into one shape — time, level, message, source, error, stack, fields — so you can filter, chart and read them. It is built for the logs of Kubernetes workloads and pipelines (argo logs, kubectl logs) and for any service that logs JSON or key=value. No folder is needed, and nothing is stored.

Opening logs#

  • Open logs…, or drop files anywhere on the tool. Several files are read as one log, merged by time; Add logs… (or Shift while dropping) adds to the open one. Each file is a chip you can remove.
  • Paste with Ctrl+V anywhere on the tool, or use Paste… for a box.
  • In the Explorer, right-click a .log, .ndjson, .jsonl or .txt file → Open in Log viewer. The Explorer lists files up to 8 MB; open bigger ones as files.

Files may be gzip-compressed or UTF-16 (as PowerShell's > writes them). A log can hold up to 256 MB of text.

What it reads#

KindExamples
ECS JSONany ecs-logging library (Go ecszap, Java, .NET, Python, Node): @timestamp, log.level, message, error.*, trace.id; dotted or nested fields
Other JSONGo slog, zap, logrus, zerolog; Bunyan and pino; Serilog (message templates filled in); Docker's container log files; Kibana and Elasticsearch exports
logfmttime=… level=info msg="…" key=value: slog's text handler, logrus, Argo's own containers
TextKubernetes klog, Go's log package, timestamped lines with a level word; Go panics and Java, .NET, Node and Python stack traces, joined to the entry they belong to
Prefixesargo logs and stern pod names, kubectl logs --prefix and --timestamps, container runtime lines, docker compose logs, CI timestamps and colour codes are taken off and kept as the entry's source and time

Lines from different pods may interleave; a stack trace still joins its own pod's entry. A message that is itself JSON is read as fields too (msg.user.id). A line codec can't place is kept as a text entry, so nothing is lost.

The overview#

Above the entries: how many there are and over how long, the count per level (click one to show it and worse), the sources and formats, a link to the first error, the errors that repeat most (messages that differ only in numbers, IDs, UUIDs or quoted values count as one) and the longest silences, when nothing was logged.

Filtering#

Type a query and press Enter; All · Info+ · Warn+ · Errors writes the level part for you. Terms are combined with AND.

QueryMatches entries…
timeout, "connection reset"containing the word or phrase anywhere, ignoring case
/time.?out/matching a regular expression (Go's RE2)
level>=warn, level:errorat or above a level, or at exactly that level
service.name:api, url.path:/api/*whose field has the value, ignoring case (* is a wildcard); field:* means the field is there
status>=500, latency<1.5scomparing numbers or durations
-logger:health, NOT …without the term
a OR b, (a OR b) c, level:(error OR fatal)either one; parentheses group

Short names reach the core fields whatever the log calls them: level, message, source, logger, caller, error, stack, trace, format, file. Any other name is a field (http.response.status_code, or log.level for the level as written). A field the log doesn't have is pointed out; with : it is searched as text instead, so http://… works.

Entries over time#

The chart counts the matching entries over time, stacked by level. Drag across it to keep only that time range; the range's chip clears it.

The entries#

One row per entry: time, level, source (when there are several) and message, plus any field as a column (Columns; your choice is remembered). Times can be local, UTC or since the first entry; Wrap shows long messages whole. Rows are fetched as you scroll, so 100,000 entries scroll like 100.

↑ ↓ (or J K) move through the entries, E and Shift E go to the next and previous error, / to the query, Esc closes the entry.

An entry#

Select a row for the entry in full: its message (JSON in it laid out), error, time, source, logger, caller and trace; its stack trace, with each frame's function apart from its file and the runtime's and frameworks' frames folded away; its fields as a tree; the entries just around it (±5, 20 or 50, whatever the query hides — what led up to it); and the line as it was read.

Next to any value: only this and hide this add a term to the query, the column button shows the field in the list, and for trace, span, request and correlation IDs follow replaces the query with that ID, so you see everything that happened to one request across the log.

Errors and fields#

Errors lists the warnings and errors of the matching entries grouped by message (numbers, IDs, UUIDs and quoted values don't split a group), most frequent first, with when they started and stopped and how many sources had them. Click one for its first entry; Show filters to it (group:3).

Fields lists every field of the matching entries: how often it is there, its most common values (click one to filter to it) and, for numbers, the minimum, median, 95th percentile, maximum and mean.

Export and copy#

The export button saves the matching entries as the lines they were read from (.log), as one JSON object each (.ndjson) or as a table with your columns (.csv). Alt C copies a short summary of the log; an entry's buttons copy its line or the entry as JSON. Whatever is copied has likely secrets masked — values of password, token, secret, key and cookie fields, bearer credentials, JWTs and passwords in URLs — so it is safer to paste into a ticket. Masking is a safety net; read what you share.

Where the log is kept#

The log is read by codec's server and held in its memory while you look at it — never written to disk. A log unused for an hour is let go, and so are the oldest when the logs held reach 1 GB of memory; the tool then sends it again from what it still holds, without asking. Closing the log, or codec, lets it go.
